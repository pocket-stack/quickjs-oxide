上游机制与容易误读的细节

MEMORY SNAPSHOT

-d：执行后取一次快照

JS_ComputeMemoryUsage 收集 runtime 分配统计及对象图分类，随后 JS_DumpMemoryUsage 格式化输出。

正常执行路径在 js_std_loop 返回后、释放 Context / Runtime 之前打印。命令行求值进入 fail: 的路径不会经过这次 dump；不能假设每种失败退出都有报告。

ALLOCATION TRACE

-T：替换 allocator 回调

CLI 通过 JS_NewRuntime2(&trace_mf, ...) 注入 malloc / realloc / free 包装函数，打印 A / R / F 事件。

覆盖经过该 runtime allocator 的调用，不是所有 libc 分配或进程 RSS。没有函数调用栈或事件时间戳；指针显示为相对基址偏移及可用大小。

INSTANTIATION COST

-q -d：四个阶段分别取最好值

在常规初始化、dump 和释放之后，额外重复 100 次 JS_NewRuntime → JS_NewContext → JS_FreeContext → JS_FreeRuntime，用 C clock() 计时。

最终总数是四段各自最小值之和，不一定来自同一次迭代。它测的是基础 API 生命周期，不包含进程启动，也不同于装载全部 CLI 宿主功能。

OPERATION BENCHMARK

微基准：逐步扩大工作量

按计时阈值扩展循环次数，重复采样并取较短的单位操作时间，输出 ns/op。支持参考结果比较与全套结果保存。

本版本每档至多 100 次测量，最多 30 档；时钟依次选择 performance.now、os.now、Date.now。这些是基准驱动行为，不是 CPU profiler。

组合开关会改变观测：-T -d 时，dump 格式化中的对象大小探测也可能产生 A/F 事件；初始化与销毁也被跟踪。-T -q -d 后面的 100 次计时使用普通 JS_NewRuntime，不会继承 trace allocator。不要把 trace 日志当成纯业务分配，也不要带 trace 测正常执行速度。

上游 -d 不额外显式调用一次 JS_RunGC。我们也不应为了“看起来内存更少”在快照前偷偷强制 GC。需要 GC 后快照时，应作为独立实验明确标注。

固定观测口径，不固定内部实现

Rust 可以使用不同的对象表示、arena、共享字符串或分配策略。复现的契约应是同一阶段、同一资源范围、清楚的计量单位，不要求复现 QuickJS 的结构体尺寸或内存地址。

指标上游含义Oxide 的报告要求
malloc_count / malloc_sizeruntime allocator 的当前存量；size 受 usable-size 与平台开销定义影响。只在覆盖完整时报告对应分配量；区分 requested / capacity / usable。无法获取的值报告 unavailable，不填 0。
memory_used_size遍历 runtime 数据得到的分类统计口径。独立于 allocator 总量，说明估算规则和共享资源去重规则；不能用 节点数 × size_of 冒充完整占用。
对象、shape、atom、字符串、函数代码等逻辑资源类别的 count / size。先复用已有节点计数；字节统计由资源拥有者提供。String buffer、Vec capacity、共享 backing store 必须有唯一归属。
A / R / F一次 runtime allocator 调用及其结果。建议使用不暴露地址的 allocation ID；记录请求大小、结果和失败。不要把创建 JSObject 等同于一次 malloc。
基础生命周期耗时CPU time；四段分别取最小值。若用 Rust Instant，明确标注 wall time；不得给两种时钟的结果直接计算加速比。
峰值 / RSS / 累计分配量不是 -d 中“当前使用量”的同义词。可以将来扩展为独立字段，注明来源；本轮不借用上游名称混报。
精确分配跟踪有前提：当前工程禁止 unsafe code。完整拦截 Rust allocator 可能涉及 allocator 层改造，不能仅靠给 heap 节点增减计数实现。先确认可行的分配接入范围；如果只能覆盖部分资源，报告必须带 coverage=partial。本报告不要求改变 unsafe 策略，也不宣称 -T 能无条件完整复刻。

建议输出携带 schema、引擎版本、提交、构建配置、平台 / 指针宽度、runtime 标识、快照阶段、资源覆盖范围及计量依据。字段可以稳定，采集实现可以替换。上游原始文本和 Oxide 结构化数据各自保存，不伪造逐字一致。

拟议数据契约 · 示例值不是测量结果
{
  "schema": "oxide-memory-v1",
  "phase": "after-jobs-before-context-drop",
  "coverage": "partial",
  "categories": {
    "objects": { "count": 1000, "bytes": null, "basis": "node-count-only" }
  },
  "allocator": { "requested_live_bytes": null, "usable_live_bytes": null },
  "unavailable": ["object-bytes", "allocator-live-bytes"]
}

接入现有职责边界

采用“CLI 选择 → Runtime 观测入口 → 资源拥有者采集 → 格式化输出”的边界。无需把计时器或格式化器塞进每条字节码的执行路径，也无需现在确定未来的 Value 布局。

01 / SELECTapps/cli解析开关；决定输出目的地、生命周期和报告时机。
02 / COLLECTengine/api提供只读快照及构建时选择的观测配置入口。
03 / ACCOUNT资源拥有者heap、atom、value、code 各自提供明确归属的统计。
04 / REPORTCLI / 基准工具格式化、保存原始结果、比较同口径的指标。
位置拟议职责边界约束
apps/cli/src/main.rs扩展 -d、-T 和 -q -d；统一处理报告退出路径。默认 stdout 行为不变。建议观测写 stderr / 独立文件，明确区别于上游的 stdout；若需要原样 stdout，另设显式选项。
src/engine/api/暴露快照结果和 Runtime 创建时的观测选项。对外返回稳定数据，不暴露 Heap、ShapeId 或 allocator 实现。命名以实现时审查为准。
heap / atom / value / code统计各自拥有的节点、buffer、字节码和共享存储。以物理持有者或可去重的资源身份计数，防止多条引用重复计算同一存储。
分配接入层，位置待定在能力允许时生成 A/R/F 对应事件。不要借用 host 存放内部观测，也不为 profiling 重写整个 allocator。
scripts/benchmark/（拟新增）固定用例、准备两个引擎、保存元数据和结果。属于开发工具，不能成为引擎运行时依赖；不复用 Test262 正确性通过率作速度分数。

当前 heap_counts() 可复用来形成第一版逻辑快照；run_gc() 返回的 GcStats 是一次收集的节点统计，不是通用内存 profiler。新增诊断文件仍放在已有职责目录下，目录说明同步更新。

快照和跟踪不能改变什么

快照不执行 JS getter / Proxy trap，不人为推进 jobs，不增加持久 roots，也不为了计数改变对象的可达性。格式化和 I/O 留在引擎状态借用范围之外。跟踪输出避免递归进入被跟踪分配器；若有丢弃或写入失败，应标记报告不完整，不把它当作 JavaScript 异常。

上游 A/R/F 包装存在特殊路径：realloc(NULL,n) 可以表现为分配，realloc(p,0) 表现为释放语义；realloc 失败时原分配仍活着。不能假设所有失败请求都会打印一条事件。

如何启用，如何真正关闭

以下全部为 Oxide 设计草案 上游运行命令见第 03 节。当前仓库没有 profiling feature，也没有 -d / -T 支持；下列命令不能被当作已经实现。

状态预期行为关闭保证
编译不含 profiling正常执行；遇到 -d / -T 明确返回“此构建未启用观测”。移除事件缓冲、观测回调和增量计数逻辑；不悄悄忽略开关。
编译含 profiling，运行无开关不采集、不写报告、不创建日志。可能仍有代码体积或分支成本；需测量，不能直接承诺零开销。
仅 -d在约定退出阶段请求快照。下一次运行去掉 -d；无需卸载工具。
仅 -T从 Runtime 创建前启用，到该 Runtime 完全释放后结束。不支持运行中“只关事件”的首版方案；重新运行时去掉 -T，保留完整分配生命周期。
-q -d基础生命周期基准 + 初始快照，时钟口径写入报告。移除 -d 后只初始化退出；正常业务运行还需移除 -q。

拟议：构建并按需开启

尚不可运行 · CLI feature 需向引擎转发
cargo build --release -p quickjs-oxide-cli \
  --features profiling

./target/release/qjs -d target/profile/workload.js \
  2> target/profile/oxide-memory.txt

./target/release/qjs -T target/profile/workload.js \
  2> target/profile/oxide-alloc.trace

./target/release/qjs -q -d \
  2> target/profile/oxide-startup.txt

拟议：关闭与纯净构建

运行时移除开关；独立目标目录隔离构建
# 不请求任何观测
./target/release/qjs target/profile/workload.js

# 编译时完全不包含拟议 profiling feature
cargo build --release -p quickjs-oxide-cli \
  --no-default-features --target-dir target/plain
./target/plain/release/qjs target/profile/workload.js

独立目录避免误运行先前的观测二进制。Cargo feature 会合并：需保证 CLI 和引擎依赖都没有显式启用 profiling；--no-default-features 不会撤销依赖显式启用的 feature。

验收“关闭”而不是口头承诺：关闭时无观测输出、无观测文件、无事件缓冲增长；不含 feature 的构建不编译观测模块。分别比较纯净构建、含功能但关闭、dump、trace 四种模式的耗时和分配，给出测量环境与误差。

Rust 嵌入 API 首版建议将跟踪配置固定在 Runtime 构造阶段；快照可以是显式方法调用。在线暂停 / 恢复会引入“暂停前分配、暂停后释放”的状态问题，不作为首版契约。

微基准复现：尽量保持测试主体一致

固定使用 2026-06-04 发行包中的 tests/microbench.js。只适配时钟、参数、输出和结果文件能力；不要为了跑分改写属性访问、循环或调用主体。

上游 · 延续第 03 节的 shell 变量
# 选定项目：适合快速定位，不会保存全套参考 JSON
"$qjs_path" --std "$qjs_src/tests/microbench.js" \
  empty_loop prop_read \
  > target/profile/quickjs-selected.txt

# 全套运行才保存参考结果
"$qjs_path" --std "$qjs_src/tests/microbench.js" \
  -s target/profile/quickjs-reference.json

# 再运行全套并比较；同样保留新结果
"$qjs_path" --std "$qjs_src/tests/microbench.js" \
  -r target/profile/quickjs-reference.json \
  -s target/profile/quickjs-current.json

-s 与 -r 在上例中放在脚本路径之后，是 microbench 的参数；脚本之前的 qjs -s 是删除调试信息，含义不同。选定项目采用名字前缀匹配；该版本只在全套运行时保存参考文件。

第一步：最薄的宿主适配

为同一脚本提供 console.log / scriptArgs / 单调高精度时钟，检查结果文件读写能力。当前 Oxide CLI 没有上游的 --std 模式，不能直接照搬整条命令。

如果只补最小 harness，不承诺实现完整 std/os 模块。更改时钟或采样策略时，两端必须使用同一个修改后的 harness，保留补丁与哈希。

第二步：把结果变得可解释

保留上游最短时间指标以便对照；额外多次独立运行，保存原始结果与波动范围。冷启动、编译和 steady-state 执行分开测。

性能运行关闭 -T / -d，检查样本确实执行成功。无法执行的项目列为 unsupported，不算 0 ns，也不纳入汇总分数。

在 PocketLab 等固定机器上串行运行两个引擎，控制其他任务和编译配置，交替运行顺序。结果记录 CPU / OS、Rust / C 编译器、优化参数、计时器、引擎提交、用例哈希及开启的观测功能。当前没有测得 Oxide 与 QuickJS 的性能差距，本报告不提供预测倍数。

分阶段实施与验收

阶段最小交付完成条件
① 固定参照复用现有 oracle 构建，保存上游四类输出与版本。命令、产物和来源可复现；可运行与拟议状态清楚区分。本报告已做基本冒烟。
② 快照 + 生命周期feature 开关、-d、-q -d、资源统计契约。先提供可靠 count 和显式 unavailable；不虚报字节；四阶段时钟口径明确。
③ 分配覆盖评估列出哪些内存路径可被安全观测，再实现 -T。若覆盖不完整则明确 partial；realloc、失败和释放边界正确；关闭没有事件输出。
④ 可比较的微基准同用例双引擎 runner、原始结果与逐项对比。结果校验通过、样本时长足够、重复性可接受；不预设性能门槛。
  • 默认行为：同一脚本输出与异常结果一致；关闭观测后没有额外文件和打印。
  • 生命周期：覆盖跨 Context、共享字符串 / backing store、弱引用、cycle GC 和 pending jobs；共享资源不重复计数。
  • 失败路径：分配失败、realloc 失败、日志写入失败不会改变 JavaScript 的错误种类或吞掉原始异常。
  • 执行边界：快照在约定的 jobs 状态下执行；不额外推进微任务，不偷偷强制 GC；异常退出的报告策略写进规范。
  • 数据声明：allocated、used、capacity、RSS 和 peak 明确分列；不支持的指标可见，不以 0 冒充。
  • 语义验证：相关 Rust / QuickJS 对照测试及全量 Test262 无新增结果差异；正确性门禁与性能结果独立保存。
  • 发布检查：生产构建未启用 profiling；含功能但关闭的构建单独测开销，保持恢复为普通构建的明确命令。

本报告不实现 feature、CLI 参数或 allocator 插桩，也不修改 Test262 基线。实现阶段应以独立提交交付并分别验收。

本次实际验证了什么

在本地 Linux x86_64 上，使用项目现有 oracle 脚本获取的 QuickJS 2026-06-04 执行了以下冒烟验证。源码基点为 69b987b；结果只证明操作入口和输出符合说明，不构成稳定性能基线。

检查实际结果
无 -d / -T退出码 0；stdout 仅一行 profile-probe，stderr 为空。
-d退出码 0；出现分类内存表和分配统计。
