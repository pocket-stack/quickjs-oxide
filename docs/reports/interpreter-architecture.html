IMPLEMENTATION STUDY · 2026.09.08

解释器的最佳架构：
成熟实现的职责划分研究

从 CPython、Lua、V8 和 QuickJS 的真实对象与执行模型出发，判断什么应该共享、什么应该分离，以及什么根本不必成为一个独立 crate。

面向 Rust 编写的嵌入式 JS 解释器官方文档与源码对照设计建议，尚非项目决议
01 / FINDINGS

最值得采用的是边界原则，而非某棵目录树

研究结论对嵌入式解释器，优先建立职责清晰、生命周期一致的执行核心；在源码处理、编译、代码表示、执行、对象语义与宿主之间定义接口。不要把“编译器完全不接触运行时”和“公共 core 必须承载所有基础能力”当作先验要求。

01 / 核心可以包含完整值体系

Lua 的 Core 包括对象、GC、编译器和 VM。CPython 的 code object 使用 Python 对象承载常量；QuickJS 字节码也使用 JSValue。完整值体系属于执行核心，是成熟且成立的组织方式。[L1][P4][Q2]

02 / 分阶段，不等于分生命周期域

编译阶段可以有独立的数据结构和模块，同时使用运行时字符串、分配器与对象管理。Lua 是直接例子。V8 的临时堆外表示则说明：更强隔离有价值，但需要具体需求支撑。[L2][V2][V6]

03 / 代码、闭包、执行帧要分清

编译结果描述如何执行；闭包关联执行环境；帧记录某次调用的动态状态。四个实现虽字段与命名不同，都体现了这些角色的区分。它们无需分属独立发布的库。[P2][L3][V1][Q2]

04 / 所有权比“零依赖”更关键

名称表归谁、编译失败如何清理、GC 能看到哪些引用、宿主回调能否重入，比 crate 数量更能决定架构是否可维护。此为对四个实现生命周期机制的综合判断。[P11][L2][V5][Q3]

“最佳”在本报告中指：在具体需求下，能以可理解的成本保持语义正确、所有权明确、可测试、可演进。没有跨项目通用的最优目录布局，也未进行性能排名。

02 / SCOPE & METHOD

研究对象与证据范围

选择两个 C 实现的语言运行系统、两个 JS 引擎，既比较语言实现，也比较规模差异。V8 是带解释层和多级编译器的引擎，不能把它的全部复杂性都归因于“解释器”。本报告审阅实际数据结构、关键入口与官方设计说明，未构建这些上游项目，也未做吞吐、内存或编译耗时基准。

04 / IMPLEMENTATIONS

四个实际实现：边界到底在哪里

CPython

COMPILER PASSES + SHARED OBJECT SYSTEM

它展示的是：编译流程可以精细分工，同时使用统一的语言对象体系。阶段间的清晰交接，并不要求最终编译产物成为脱离解释器内存管理的纯数据。

职责如何落到源码

Parser/ 处理语法前端；Python/ 中分别组织编译、求值、异常、导入等机制；Objects/ 实现语言对象。Lib/re 和 Modules/_sre 则是库功能与底层实现的另一组边界。这样的结构不追求所有内容都进入一个通用 core。[P1][P2][P8][P9]

PyCodeObject 的常量和名称字段使用 PyObject*。源码位置表、异常表也属于 code 的元数据；调用时，Frame 再加入指令位置、局部执行状态与全局环境。代码对象和执行激活因此是不同角色，但共享 Python 的对象基础。[P4][P2]

名称、内存与源码位置

驻留字符串不是必须转换成整数 ID：CPython 直接复用字符串对象，指针比较可用于已驻留的字符串。动态字符串驻留集合属于解释器；静态单例有更广的共享范围，因此“所有 interning 都归一个 runtime-local 表”也不是通则。[P5]

AST 临时内存使用 arena；Python 对象另遵循引用所有权。对象类型要向循环 GC 提供必要的遍历协议。源码范围则压缩保存在 code 的位置表中，需要 traceback 或 tracing 时再解释，而不是让所有对象携带 TextSpan。[P1][P6][P3]

值得借鉴分离临时编译结构、可执行代码对象与一次调用的帧；将源码位置作为显式元数据。不要据此推导“编译器必须完全不依赖对象系统”。

重要反例：可序列化，不等于内存中必须纯数据化

CPython 可将 code object 用 marshal 编码，再在另一进程重新构建。内存中的 code object 仍是 Python 对象。持久化格式与运行时内存表示可以是不同层，不必让每一次编译都经过一种永久独立的公共 DTO。[P3]

Lua

ONE COHESIVE CORE, EXPLICIT MODULES

Lua 是反对“职责清晰必须拆很多库”的直接例子。官网将编译、VM、对象、字符串、GC 和 C API 都列为 Core；标准库、命令行解释器和命令行编译器另列。这个 core 的含义是语言实现内核，不是杂项工具集合。[L1]

编译和执行共享所属 Lua 全局状态的对象管理。图中的阶段是职责划分，不是相互隔离的内存域。[L2][L3][L4][L7][L8]

小型内核内部仍有清楚的分工

lparser/lcode 负责生成指令；lvm 负责执行；ldo 处理调用和错误控制；lobject/ltable/lstring/lfunc 处理表示；lgc/lmem/lstate 处理存储与状态；lapi 提供嵌入接口。它们被组织在同一个内核中，而非一组必须独立发布的组件。[L1]

luaY_parser 接收 lua_State*，直接创建 LClosure、Proto，并把临时对象放到栈上保护；向对象写入引用时执行 GC barrier。编译器确实参与运行时对象管理，这不是结构失效。它选择统一的生命周期机制。[L2]

名称表的真实形态

global_State 持有字符串表；短字符串驻留，长字符串走另一分支。scanner 还使用自己的 table 保存解析期间的字符串，避免回收。这里同时存在“共享字符串存储”和“编译期保活集合”，不能粗略归为“只有一张表”或“编译期完全独立”。[L4][L5][L6]

Proto 保存 TValue 常量、子原型和源码信息；closure 关联 upvalue。Lua 的增量/分代 GC、C API 栈及辅助库共同定义对象使用方式。字符串库提供的是 Lua patterns，不是完整 ECMAScript 正则，因此不能直接照搬它的语义规模。[L3][L8][L9]

值得借鉴对紧凑的嵌入式解释器，先建立一个按职责拆模块的核心库，通常是有力候选。把语言机制与可选标准库、应用入口分开；不必先把所有内部协作变成跨 crate API。

V8 / Ignition

COMPILATION TIERS + MANAGED RUNTIME

V8 的价值在于展示复杂需求如何产生更强的阶段隔离。它要同时处理快速启动、后台编译、优化反馈、反优化和嵌入 API；Ignition 只是执行体系的一层。不能把它的目录数量当作小型解释器的目标。[V1][V6][V7]

职责并不止于 compiler / VM

src/parsing、src/ast、src/interpreter 区分语法和字节码工作；src/objects、src/heap、src/execution 组织对象、内存与状态；src/regexp 是正则子系统。公开 handles 和 Context 则通过 embedding API 暴露给宿主。[V1][V2][V3][V4][V5][V8]

AstValueFactory 在引擎堆外保存临时字符串，之后 internalize。最终 BytecodeArray 是引擎管理的对象，带常量池、异常表和源码位置表；所读快照还区分 sandbox 内 wrapper 与 trusted-space 代码表示。“临时编译数据脱离堆”不等于“最终产物独立于运行时”。[V2][V3]

为什么要延后 materialization

2018 年官方背景编译文章明确记录：为了减少后台编译对 JS 堆的访问，V8 延后了字面量 internalization 与字节码对象构建。这是由线程与 GC 约束驱动的改动。文章中的具体主线程安排属于历史实现，不能原封不动当作 2026 年约束。[V6]

Isolate 组织执行域和内存管理；宿主通过 HandleScope 等机制维护引用。名称则既有编译期 AstRawString，也有运行时 internalized string；Symbol 属于对象模型中的身份类型。这个分工比“所有名称都是一个整数 atom”更丰富。[V4][V5][V9][V10]

值得借鉴明确临时编译分配与持久对象的交接、统一代码元数据、让调试与优化共享执行模型。只有在后台编译、JIT 或同类需求成立时，才引入对应隔离与复杂度。

不要把 src/regexp 误读成完全独立的纯算法库

V8 的正则子系统有明确目录和 API，但仍使用 Isolate、handles 和引擎对象。职责独立与部署、内存、链接完全独立是不同承诺。QuickJS 的正则接口则展示了更容易提取成独立库的另一端。[V8][Q4]

QuickJS

COMPACT ENGINE + EXPLICIT ALGORITHM LIBRARIES

QuickJS 适合研究紧凑 JS 解释器的职责，但不适合照搬文件大小和布局。它把大量引擎机制放在 quickjs.c，同时为正则和 Unicode 建立明确接口。这说明一个项目可以在不同边界上选择不同粒度。[Q2][Q4][Q5]

编译可经 compile-only 路径与执行分开，但所读内存结构仍使用 Runtime / Context 的资源。[Q1][Q2][Q3]

状态和名称共享是直接的

JSRuntime 持有 atom 表、GC 与 jobs 等状态；Context 维护 realm 相关对象。Parser 使用 Context；字节码对象包含 JSValue 常量、名称和 realm。atom 的引用通过 API 管理。因此，编译阶段与运行时共享资源是这一实现的实际选择。[Q2][Q3]

真正清楚的算法接口

libregexp.h 暴露模式编译、执行、captures 等接口，要求调用方提供分配与超时/栈检查回调；它不要求以 JSContext 或 JSValue 作为公开参数。libunicode.h 则面向 Unicode 数据操作。JS 的 RegExp 对象及其可观察语义由引擎集成。[Q4][Q5]

quickjs-libc 提供 std/os、加载和事件循环辅助，qjs 与 qjsc 是程序入口。不过，所读 Makefile 的库对象集合也包含 quickjs-libc：逻辑分工存在，不代表构建目标已经完全分离。[Q6][Q7]

值得借鉴紧凑的运行时所有权、面向嵌入的入口、正则与 Unicode 的明确接口。可以把大文件中的职责展开成模块；没有必要同时重写算法或制造第二套值体系。

共享 atom 表，也不排斥日后增加持久化

QuickJS 的字节码写出逻辑会把 atom 转成编码用索引；重新读取时再建立相应表示。这种边界转换可以发生在序列化/加载层，不必在普通编译路径中永久复制一套运行时无关模型。[Q2]

05 / BOUNDARY DECISIONS

从实现证据回到关键架构问题

core 到底是什么

综合判断core 若存在，最有解释力的含义是“语言执行核心”，而不是“被两个模块引用的代码”。Lua 的官方分类直接支持前一种含义；其他实现则用具体模块与内部对象体系表达相近职责。不存在一个必须放在依赖图最底部、又必须不含行为的标准 core。[L1][P2][Q2]

可以拥有 Value、Object、Symbol、AtomTable、GC、Code、Frame 与语言内置行为。也可以不用 core 这个名字，直接叫 engine。关键是边界能否解释什么属于它，而不是名字是否“底层”。通用 bytes、span、字符串算法不能仅因为基础就与整个执行内核混为一谈。

编译器是否应该依赖运行时

综合判断没有统一禁令。Lua 编译器直接创建受 GC 管理的原型；CPython 编译产物使用对象体系；V8 同时存在临时堆外表示和最终引擎对象。因而应分别回答编译算法依赖什么、使用谁的资源、结果绑定哪个域。[L2][P4][V2][V3]

在一个 crate 内分 compiler 与 vm 模块，两者共用 runtime 数据，是合法且可能更简单的选择。如果需要独立编译服务、后台线程或专门缓存格式，再加强交接契约。没有跨运行时复用需求，只排除了一个拆分动机；并不自动证明共享方案性能更优。

atom：先决定语义域，再决定表与 ID

观察CPython 复用驻留字符串对象；Lua 短字符串驻留但 scanner 还有保活集合；V8 使用临时 AST 字符串再 internalize；QuickJS 直接使用 Runtime atom。四者没有共同的整数编号形式。[P5][L5][L6][V2][Q3]

建议固定三个约束：文本名称按内容规范化；Symbol/私有身份不能按描述合并；任何 ID、指针或 handle 都必须说明适用域和保活方式。表实现放在哪里、表实例归谁、编译结果是否保留同一身份，是三个独立选择。普通名称与独特身份可以共享存储，也可以分离；不要让 compiler 获得不需要的身份创建或释放能力。

编译常量必须有单独的 PrimitiveValue 吗

综合判断不是解释器架构的必要条件。Lua 原型使用 TValue，CPython 使用 PyObject；这不意味着任意可变对象都允许作为源码常量，而是表示类型与合法构造规则可以分开。[L3][P4]

若限制常量种类能在 Rust 类型层防止错误，可以定义 Literal 或 Constant；若统一 Value 已能表达必要数据和所有权，也可以用专门构造器约束。不要为了拆 crate 而自动引入一套重复的 JS 类型转换、相等性和字符串语义。是否包含 Symbol，应由该类型承诺的范围决定，不应把编译常量误称为完整 JS 原始值体系。

TextSpan 贯穿流程，但不必贯穿所有对象

观察CPython 的 code 位置表、Lua Proto 的行信息、V8 的 source-position table 和 QuickJS 的调试信息，都在连接编译和诊断。数据粒度各不相同，没有统一的 span 结构。[P3][L3][V3][Q2]

建议source 层定义源码身份、偏移单位和范围；compiler 构建 PC → source 映射；执行帧记录当前 PC；诊断层按需恢复位置。不要为了“贯穿”让对象、GC 节点或每条热路径操作都存 TextSpan。UTF-8 字节、UTF-16 码元与显示列必须明确区分——例如 Python AST 文档明确使用 UTF-8 字节列偏移。[P10]

GC、对象、语言行为不适合机械切成无依赖层

观察CPython 类型提供遍历支持，Lua 写入对象引用时执行 GC barrier，V8 handles 配合 GC 维持有效引用。对象形态与回收方式之间有实际协议。[P6][L2][V5]

建议把对象布局、边遍历、分配、回收与外部 roots 设计为一致系统。可以拆模块乃至 GC 库，但要有明确 trace/barrier/root 契约。不要为满足 crate DAG，令回收器通过含义模糊的回调反向操纵整个引擎。JS 属性访问、getter、Proxy、coercion 和调用还可能互相触发；模块协作应受控，而非假装它们是一条单向流水线。

语言内置行为与宿主功能是不同边界

综合判断正则算法、RegExp 对象语义、文件加载、定时器和 CLI 输出不是同一责任。QuickJS 提供独立正则接口及 libc 辅助层；Lua 将语言内核与库分组；V8 embedding 让宿主接入外部能力。[Q4][Q6][L1][V5]

对 JS，引擎仍须负责语言规定的 Date、Promise、RegExp 等行为；宿主提供其依赖的时间、加载、调度或输出能力。不要把“不是 VM 指令执行”一律归到 host，也不要把“是标准库”一律视为可随意删去的语言语义。

07 / RUST ORGANIZATION

Rust 落地：先模块，后决定哪些值得成为 crate

项目建议已知讨论背景是 Rust JS 解释器、嵌入与应用入口，且没有编译产物跨运行时复用要求。后台编译、独立语法工具、JIT 和稳定字节码格式尚未被设为目标。基于这些信息，下面给出首选候选和替代方案；它们均未替用户作出架构决议。

候选 A：按模块分工的完整 engine

落地记录（2026-09-08）：本项目已选定候选 A；src 顶层仅保留 lib.rs，source、regexp 与 engine 为同级模块，解释器实现按下列职责拆分。具体目录与接口见 Workspace architecture。下文保留研究时的候选比较与原始结论。

以 Lua 的内核组织为主要参考、借用 QuickJS 的算法接口分离，先让编译、代码与执行共享一个清楚的内部模型。这可以减少为了跨 crate 可见性引入的抽象；收益是结构简洁，代价是编译器不天然成为可独立使用的产品。

source/                   # 源码身份、范围、坐标；可复用组件
regexp/                   # 正则程序、编译、匹配及受限回调
engine/
  compiler/               # 词法、解析、作用域、字节码生成
  code/                   # 指令、常量、函数代码、异常与位置表
  value/  object/         # 完整值体系与对象语义
  atom/  heap/            # 名称身份、存储、回收与 roots
  vm/                     # 帧、调用、执行与挂起
  realm/  builtins/        # 环境初始化、语言内置行为
  modules/  jobs/          # 模块实例与待运行计算
  host/                   # 引擎请求的环境能力接口
  api/                    # Rust 嵌入边界
adapters/                 # 本机 / Web 的服务提供者
apps/                     # CLI、playground 等产品入口
conformance/              # 语言一致性测试驱动

只是职责目录示意，不是待应用的 Cargo workspace。source、regexp 是否独立 crate 有清楚的复用理由；Unicode、string、numeric 是否再拆，应看真实消费者和 API，不预先规定包数量。

候选 B：需要独立 compiler 时再建立共享契约

若出现独立编译服务、IDE 语法工具或后台线程，compiler 与 engine 可以分成 crate。此时有两条路径：共用一个不依赖执行器的表示/存储组件；或由 compiler 输出独立表示、engine 负责接入。前者仍可绑定同一运行时资源，后者提供更强隔离。避免 crate 循环，只要求模块依赖方向成立，并不要求跨运行时可移植。

方案适合什么需求主要成本 / 风险如何验证
A · 统一 engine 内分模块嵌入、快速执行、共享对象系统；维护一个解释器产品内部依赖容易扩散，需控制可见性和公共入口关键路径可单独测试；修改语法是否迫使无关存储实现一起修改
B1 · compiler / engine 共用存储契约希望独立构建和测试 compiler，同时复用同一名称与对象资源共享组件可能膨胀；“受限接口”可能退化成整个 Runtime列出 compiler 实际需要的操作，检查是否包含执行、宿主副作用或任意堆变更
B2 · compiler 输出独立产物明确的独立编译、线程隔离、传输或复用需求重复表示、名称映射、materialization 和额外失败路径编译总耗时、峰值内存、转换成本；隔离目标是否真正实现

本报告倾向 A 作为需求有限时的初始候选。这是基于复杂度与已知目标的工程判断，不是测量得出的性能胜者。没有跨运行时复用要求，会削弱 B2 的一个理由；若后续有独立分析或并行编译需求，应重新比较。

crate 边界的四个实用准入条件

  1. 消费者独立：有多个真实使用方，不只是未来可能使用。
  2. 契约可描述：能用少量类型、操作与生命周期规则说明功能，而不暴露整个内部 Runtime。
  3. 所有权可关闭：分配、保活、回收、错误、回调与中断规则在边界上完整。
  4. 成本有依据：复用、测试、依赖控制或构建收益，值得新增 API 与转换成本。

这些条件并非要求全部满足才可拆分，而是评估依据。Rust 可以用私有模块、pub(crate) 和受限借用先建立边界；trait 只在确实有多个实现、隔离副作用或改善测试时引入。不要为每个模块生成一个 trait，也不要为了维持一个名叫 core 的库而泛型化所有对象句柄。

08 / DECISION RECORD

接下来应该决定什么，而不是继续逐个类型争论

先定三个产品级选择

  1. 编译器是不是独立产品？只为引擎服务，还是要支持独立解析/编译调用者？
  2. 编译是否要并发或跨域？没有跨运行时复用要求已知；后台线程和缓存格式仍需由真实需求决定。
  3. 值的存活规则是什么？运行时内所有权、宿主 roots、闭包与挂起任务共享一套清楚规则。

之后用关键场景验收边界

  • 编译途中失败：临时名称、字符串和对象能完整释放。
  • 嵌套函数与闭包：代码、捕获环境、激活帧分别保活。
  • eval / 动态函数：能获得所需作用域，不获得多余权限。
  • 宿主回调与异常：重入、挂起和清理规则一致。
  • 模块、jobs 与调试：异步存活和源码定位不依赖已经销毁的临时结构。

比较两种方案时，应测编译加首次执行总时间、峰值内存、名称驻留/映射开销和变更影响范围。仅比较 VM 热循环速度，或仅看 crate DAG，都不能证明整体架构更优。这些是后续验收建议，本报告没有宣称已运行相关实验。

本报告研究阶段的交付范围：上游研究与目标设计建议。未对当前代码架构作保留背书，未把之前的候选草案升级为决定，也未执行源码重构。每个 crate / app 的 README 仍应在职责讨论定稿后补充。
